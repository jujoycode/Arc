# GitHub·GitLab 연동 설계 기준

> 상태: 제공자 인증·연결 API·서명 검증·비동기 이슈 연결 구현과 로컬 수용 검사 완료. 설정·상세 UI 검증 진행 중.

## 사용자 목표

프로젝트에 코드 저장소를 연결하고 커밋, Pull Request 또는 Merge Request의 제목·본문에서 `ARC-123` 같은 이슈 키를 인식해 해당 이슈의 개발 활동으로 보여 준다. 연동이 없어도 Arc의 이슈·간트·보드는 독립적으로 작동한다.

## 경계

- `RepositoryProvider` 경계를 두고 GitHub·GitLab 인증, 저장소 조회, 웹훅 서명 검증, 이벤트 변환을 각각 구현한다.
- 두 제공자의 이벤트를 `CommitLinked`, `ChangeRequestOpened`, `ChangeRequestMerged` 같은 Arc 내부 이벤트로 정규화한다.
- Arc 프로젝트 키와 이슈 번호는 변경되지 않는 외부 참조로 사용한다. 키 일치만으로 이슈 상태를 자동 변경하지 않는다.
- 연결 단위는 Arc 프로젝트와 외부 저장소의 조합이다. 연결 생성·해제는 프로젝트 관리자 이상만 할 수 있다.
- 연결 비밀값은 서버에서 암호화해 보관하고 브라우저 응답·로그·Git 저장소에 넣지 않는다. 제공자별 최소 권한을 요청한다.
- 웹훅은 서명 검증, 전달 ID 기반 중복 제거, 재시도와 실패 기록을 갖춘다. 외부 API 장애가 Arc 이슈 저장을 막지 않도록 비동기로 처리한다.

## 이후 추가할 데이터

Flyway V6에 `repository_connections`(프로젝트·제공자·저장소 식별자·상태), `development_links`(이슈·외부 URL·종류·상태), `webhook_deliveries`(전달 ID·처리 결과)를 추가했다. 접근 권한 확인이 실패하면 연결을 비활성화하고, 해제 시 암호화된 토큰·검증키를 비우며 기존 개발 링크를 보존한다.

## 구현 범위

GitHub.com·GitLab.com을 지원한다. 저장소 API로 읽기 권한을 확인한 뒤 연결을 저장한다. 외부 HTTP 호출 동안 DB 트랜잭션이나 프로젝트 잠금을 잡지 않고, 저장 직전에 권한을 재검사한다. OAuth 설치·제공자 이슈 동기화·GitLab 자체 호스팅은 이 단계의 범위 밖이다.

`ARC_INTEGRATION_ENCRYPTION_KEY`는 base64로 인코딩한 32바이트 키다. 비어 있으면 앱은 실행되지만 새 연동은 비활성화된다. 한 번 생성해 서버에서 보관하며 DB 백업과 함께 복구할 수 있도록 별도로 안전하게 보관한다. 임의로 바꾸면 기존 자격 증명을 복호화할 수 없다. AES-GCM은 연결 범위·필드별 AAD를 사용하고 HTTP 응답·로그에 토큰과 검증키를 포함하지 않는다.

GitHub은 원본 본문의 HMAC-SHA256, GitLab은 검증 토큰을 비교한다. 전달 ID와 저장소 식별자를 확인하고 최대 1MiB 본문만 받는다. 전달 ID는 연결별로 중복 제거한다. DB 큐는 2초 간격으로 처리하고 실패를 최대 5회 지수 간격으로 재시도한다. 관리자는 최근 20개 전달의 상태를 확인하고 실패를 다시 요청할 수 있다. 처리된 본문은 비우며 전달 ID는 보존한다.

개발 링크는 연결된 Arc 프로젝트의 현재 이슈 키·번호에만 연결한다. 이슈 상태·버전은 변경하지 않는다. 제공자 타임스탬프를 비교하고 병합 상태를 유지해 늦은 이벤트가 덮어쓰지 않게 한다. 삭제한 워크스페이스나 보관 프로젝트의 이벤트는 이슈에 연결하지 않는다.

단위 검사는 서명·본문 변조, 암호문 변조·다른 연결 범위, 제공자 경로·인증 헤더·리다이렉트 금지, 이벤트 변환을 확인한다. `scripts/integration-smoke.py`는 실제 MySQL과 로컬 HTTP 제공자 모형에서 권한·연결·GitHub/GitLab 웹훅·중복·순서·범위·실패 재시도·권한 상실·해제를 검증했다. 실제 저장소 자격 증명과 외부에서 접근 가능한 Arc 주소는 아직 제공되지 않아 실계정 웹훅 전달은 별도 설정 후 확인해야 한다.

## 첫 연동 단계의 수용 기준

1. 관리자만 저장소를 연결·해제한다.
2. `ARC-123`이 포함된 커밋과 Pull/Merge Request가 해당 이슈에 한 번만 연결된다.
3. 존재하지 않거나 다른 워크스페이스의 이슈 키는 연결되지 않는다.
4. 웹훅 재전송, 순서 변경, 제공자 일시 장애에도 중복 또는 이슈 상태 오염이 없다.
