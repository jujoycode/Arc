# 대량 데이터·실패 복원 점검

> 2026-10-06 · 두 코어·8GiB, Node 24.19, Chromium 153, 1440×1000, MySQL 8.4.

별도 워크스페이스에 이슈 5,000개를 넣고 실제 API·프로덕션 웹 번들의 간트·보드·백로그를 열었다. 페이지 조회, 통합 간트, 모든 이슈 표시, 런타임 오류, 스크롤, 백로그 첫·마지막 페이지와 전체 정렬 변경을 확인했다. 간트 순수 모델은 단일 그룹 및 100개 버전 분산 조건에서 1,000/5,000/20,000개를 측정했다.

## 변경과 관찰

- 간트 그룹마다 기존 배열을 복사하던 동작을 제거했다. 단일 그룹 20,000개의 행 생성·필터 중앙값은 약 3.3초에서 0.07~0.2초로 줄었다. 한국어 일정 레이블은 `Intl.DateTimeFormat`을 재사용한다.
- 목록 취합은 최초 페이지 이후 최대 4페이지를 병렬로 받고 취소 신호를 전달한다. 응답 순서는 페이지 순서로 유지한다.
- 보드는 `content-visibility`로 화면 밖 그리기를 지연한다. 링크·상태 선택·키보드 접근은 유지한다. 간트에 적용한 실험은 스크롤 지연을 늘려 제외했다.
- 백로그는 100개씩 표시한다. 검색 변경은 첫 페이지로 돌아가며 정렬은 전체 순서와 페이지 경계의 이전·다음 항목을 유지한다.

| 5,000개 fixture | 최초 점검 | 개선 후 관찰 |
| --- | ---: | ---: |
| 간트 화면 준비 | 6.1초 | 2.2~3.0초 |
| 보드 화면 준비 | 5.3초 | 1.9~2.7초 |
| 백로그 화면 준비 | 3.5초 | 1.2초 |
| 백로그 문서 노드 | 약 45,000 | 약 1,000 |

5,000개 전체 정렬 저장·재조회는 약 5.5초, 간트 응답은 약 2.3MB였다. 이 수치는 JIT·캐시·동시 작업에 영향을 받는 로컬 관찰치이며 통계적 비교나 응답시간 보증은 아니다. 간트·보드는 전체 DOM을 유지하며 스크롤에서 긴 프레임이 관찰됐다. 더 큰 규모는 가상화·응답 압축·서버 조회 개선 대상으로 둔다. 대량 PNG/PDF 출력은 이 점검 범위 밖이다.

## 실패 복원

백로그 정렬·편성 중 중복 변경을 막고 실패 시 최신 목록을 다시 조회한다. 브라우저 검사는 강제 409에서 순서가 유지되고 재시도 후 오류가 지워지는지 확인한다. MySQL API 검사는 유효한 이슈를 먼저 정렬한 뒤 다른 프로젝트의 이슈에서 실패하면 앞선 순서·버전 변경도 롤백되는지 확인한다. 보드 이동 실패 복원과 편집 충돌 시 입력 보존도 통과했다.

## 재현

순수 모델은 Node 24에서 실행한다. 한 번 예열한 뒤 6회의 중앙값·최댓값을 출력한다.

```bash
node scripts/gantt-benchmark.mjs
```

실제 점검은 **개발 또는 별도 테스트 설치**에서 실행한다. MySQL 컨테이너는 API가 사용하는 DB여야 하며 `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE`가 필요하다. 생성한 프로젝트가 같은 DB에 있는지 확인하고 fixture를 넣는다.

```bash
ARC_PERF_MYSQL_CONTAINER=arc-ci-check-mysql \
ARC_PERF_ISSUES=5000 \
ARC_API_URL=http://127.0.0.1:18086/api/ \
ARC_WEB_URL=http://127.0.0.1:15179 \
ARC_MAIL_URL=http://127.0.0.1:18025/api/v1/ \
node scripts/performance-smoke.mjs
```

보고서는 `.ci-artifacts/performance.json`에 기록한다. 화면 준비는 전체 간트·보드와 백로그 첫 페이지의 표시 완료까지다. 종료 시 워크스페이스를 논리 삭제하므로 테스트 DB는 별도로 폐기한다. GitHub CI에는 시간 변동이 큰 부하 검사를 필수 게이트로 넣지 않고 오류 복원·접근성·기능 수용 검사를 유지한다.
