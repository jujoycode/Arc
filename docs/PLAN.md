# Arc 프로젝트 계획

> 상태: MVP 설계 초안 · 2026-10-04

## 1. 목표와 확정된 방향

Arc는 소규모 팀이 이슈를 등록하고, 담당자를 정하고, 작업 진행을 함께 추적하는 웹 기반 프로젝트 관리 도구다.

- 첫 릴리스는 팀용 MVP로 만든다.
- 칸반과 스크럼을 모두 첫 릴리스에 포함한다.
- Redmine 수준의 간트 차트를 주요 기능으로 먼저 구현한다.
- 간트, 칸반, 스크럼은 같은 프로젝트와 이슈 데이터를 사용한다. 어느 화면에서 변경해도 상태와 일정이 즉시 일치해야 한다.
- 이슈는 Jira처럼 Epic·Story·Task·Bug·하위 작업의 계층을 갖는다.
- 팀원은 이메일로 로그인한다.
- 기술 구성: React 19 프런트엔드, Kotlin + Spring Boot 백엔드, MySQL 8 데이터베이스.
- 디자인은 KRDS를 기반으로 Arc 고유의 디자인 시스템을 확장한다.
- GitHub·GitLab 연동이 가능한 경계를 설계하되 실제 연결은 후속 단계로 둔다.

## 2. 핵심 사용자 흐름

1. 관리자가 워크스페이스를 만들고 팀원을 이메일로 초대한다.
2. 프로젝트를 만들고 이슈를 등록한다.
3. Epic 아래 Story·Task·Bug와 하위 작업을 만들고 담당자, 일정, 완료율, 관계를 지정한다.
4. 간트 차트에서 계층·기간·진행률·선행 관계를 확인하고 일정을 조정한다.
5. 팀원은 칸반 보드에서 상태를 바꾸거나 댓글로 협업한다.
6. 스크럼을 사용할 때는 백로그에서 이슈를 골라 스프린트를 계획하고 시작한다.
7. 스프린트 보드에서 같은 이슈를 추적하고, 종료 시 완료 결과를 확인한다.

## 3. 첫 릴리스 범위

### 팀과 프로젝트

- 이메일 로그인, 팀 초대·수락, 로그아웃
- 워크스페이스와 프로젝트 생성·수정
- 역할: 소유자, 관리자, 멤버
- 첫 릴리스에서는 워크스페이스의 모든 멤버가 그 안의 프로젝트를 볼 수 있다고 가정한다. 프로젝트별 비공개 권한은 후속 범위다.

### 이슈와 협업

- 이슈 생성·조회·수정·삭제
- 프로젝트별 고유 이슈 번호(예: ARC-123)
- 제목, 설명, 유형(Epic·Story·Task·Bug·하위 작업), 상태, 우선순위, 담당자, 작성자, 시작일·종료일, 완료율, 스토리 포인트
- Epic/Story/하위 작업 계층, 버전/마일스톤, 선행·차단 관계
- 기본 상태: 할 일 → 진행 중 → 검토 → 완료
- 댓글과 주요 변경 활동 기록
- 제목·번호 검색, 상태·담당자·우선순위·유형 필터

### 간트 차트

- 프로젝트·버전·Epic·이슈 계층과 기간 막대, 완료율, 오늘 선, 주말 음영
- 선행·차단 관계선, 날짜 범위와 확대·축소, 필터·저장된 보기, 표시 열 선택
- 이슈 상세로 이동, PDF·PNG 내보내기
- 세부 기준은 [Redmine 간트 기능 검토](GANTT_REFERENCE.md)를 따른다.

### 칸반

- 프로젝트 이슈를 상태별 열로 표시
- 드래그로 상태 변경
- 담당자·우선순위 필터
- 스프린트에 속하지 않은 이슈도 표시

### 스크럼

- 우선순위를 정렬할 수 있는 백로그
- 스프린트 이름·목표·기간 설정, 이슈 편성
- 스프린트 시작·종료와 진행 중 스프린트 보드
- 프로젝트당 진행 중 스프린트는 한 개
- 종료 시 완료·미완료 이슈와 스토리 포인트 요약
- 미완료 이슈는 백로그로 돌리거나 다음 스프린트로 옮길 수 있으며, 지난 스프린트 참여 기록은 보존

## 4. 기술 설계 초안

- **프런트엔드:** React 19 + TypeScript. KRDS 기반 Arc 토큰과 컴포넌트로 프로젝트 목록, 이슈 상세, 간트, 칸반, 백로그, 스프린트, 팀 설정 화면을 구성한다.
- **백엔드:** Kotlin + Spring Boot REST API. 로그인, 멤버십·역할 검사, 이슈와 스프린트의 상태 전환을 서버에서 처리한다.
- **데이터베이스:** MySQL 8. 스키마 변경은 버전 관리되는 마이그레이션으로 적용한다.
- **주요 데이터:** 사용자, 워크스페이스, 멤버십, 초대, 프로젝트, 이슈 계층과 관계, 버전, 댓글, 활동 기록, 스프린트, 이슈의 스프린트 이력, 저장된 보기.
- **보안:** 모든 조회·변경 요청에서 로그인과 워크스페이스 소속을 검사한다. 초대·역할 변경·프로젝트 설정은 소유자/관리자에게 제한한다. 인증 정보와 메일 발송 비밀값은 저장소에 넣지 않는다.

예상 저장소 구조:

```text
frontend/  React 19 앱
backend/   Kotlin + Spring Boot API
docs/      제품·기술 문서
```

## 5. 구현 순서

1. **디자인·기능 기준:** KRDS 기반 Arc 디자인 시스템, 화면 흐름, Redmine 간트 기준, API 계약, 권한 표 작성
2. **기반 구축:** React·Spring Boot·MySQL, 이메일 로그인, 워크스페이스·팀 초대
3. **공통 이슈 모델:** 프로젝트, Epic/Story/Task/Bug/하위 작업, 일정·관계·버전, 댓글, 검색·필터
4. **간트 우선 구현:** 계층·막대·진행률·관계선, 기간 이동·필터·저장된 보기, PDF·PNG 출력
5. **칸반·스크럼:** 상태별 보드와 백로그, 스프린트 계획·시작·종료
6. **검증·출시:** 권한 격리, 세 보기의 상태 동기화, 동시 수정, 접근성·반응형 화면, 배포 점검

## 6. 완료 기준

- 관리자가 팀원을 초대하고 프로젝트를 만든 뒤 이슈를 배정할 수 있다.
- 멤버가 칸반에서 변경한 이슈 상태가 스프린트 보드와 이슈 상세에 동일하게 나타난다.
- 백로그 이슈를 스프린트에 넣고 시작·종료할 수 있다.
- 스프린트 종료 후 미완료 이슈를 이월해도 지난 스프린트 결과가 남는다.
- 다른 워크스페이스의 사용자는 해당 데이터에 접근하거나 수정할 수 없다.
- 새로고침하거나 다른 기기에서 로그인해도 작업 내용이 유지된다.
- Redmine 기준의 계층·일정·진행률·관계·필터·확대·내보내기를 간트에서 사용할 수 있다.

## 7. 다음 단계로 미루는 기능

파일 첨부, 알림, 맞춤형 상태·필드, WIP 제한, 번다운·속도 차트, 자동화, GitHub·GitLab 실제 연결.

## 8. 구현 전에 결정할 사항

- 이메일 로그인은 우선 이메일·비밀번호 방식으로 설계한다. 다른 방식이 필요하면 인증 기능 구현 전에 변경한다.
- 메일 발송 서비스와 배포 환경
- 첫 관리자 생성 방법과 초대 메일 운영 방식
