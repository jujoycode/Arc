# 워크스페이스 티켓 필드 설정

> 갱신일: 2026-10-10 · 사용자 확정 범위: 표준 필드 설정 + 커스텀 필드 추가
> 구현 기준: [폼 디자인](FORM_DESIGN.md), [기능 명세](FUNCTIONAL_SPEC.md)

워크스페이스 전체가 같은 티켓 양식을 사용한다. 개인별 보기 설정과 구분하며, 프로젝트의 실행 흐름과 기존 데이터는 유지한다.

## 권한과 적용 범위

워크스페이스 소유자·관리자가 필드 정의를 설정한다. 프로젝트 관리자는 티켓 계획과 커스텀 값을 편집한다. 개발자는 기존처럼 담당 티켓의 상태·완료율만 편집하며 팀원 모두 댓글을 작성할 수 있다. 보관 프로젝트는 읽기 전용이다. 추가 프로젝트 관리자 지정은 워크스페이스 필드 설정 권한을 부여하지 않는다.

설정은 해당 워크스페이스의 모든 프로젝트에 적용한다. 프로젝트별 재정의, 개인 양식, 맞춤 워크플로는 이번 범위에 포함하지 않는다.

## 표준 필드

- 레이블·설명·표시 여부·필수 여부·그룹 내 순서를 설정한다. 타입과 API 키·상태·유형의 의미는 고정한다.
- 제목·유형·상태·완료율은 항상 표시하며 필수다. 티켓 키는 서버가 발급하는 읽기 전용 식별자다.
- 설명·우선순위·담당자·시작일·마감일·추정치·상위 티켓·버전은 허용된 범위에서 설정한다. 숨김과 필수를 동시에 지정할 수 없다.
- 상위 티켓은 유형의 기존 규칙을 따른다. 하위 작업은 상위 티켓을 반드시 표시하고 요구한다. Epic의 상위 티켓은 허용하지 않는다. 일반적인 상위 티켓 필수 설정은 제공하지 않는다.
- 숨긴 필드의 저장값과 기존 기본값을 보존한다. 기본 필드 설정을 아직 저장하지 않은 워크스페이스는 기존 양식을 사용한다.

## 커스텀 필드

| 타입 | 입력과 저장 규칙 |
| --- | --- |
| TEXT | 최대 2,000자, 빈 값은 null |
| NUMBER | 유한한 숫자, 절댓값 10억 이하, 소수점 최대 6자리. 0과 빈 값 구분 |
| DATE | 실제 날짜인 YYYY-MM-DD |
| SELECT | 안정적인 선택지 키와 표시 이름. 단일 선택 |

필드에는 안정적인 키, 타입, 레이블, 설명, 필수 여부, 순서, 활성 여부를 저장한다. 활성 커스텀 필드는 최대 30개다. 생성 후 타입은 변경하지 않는다. 필드와 선택지를 비활성화하여 기존 값을 보존하며, 기존 비활성 선택지는 값이 그대로인 경우 유지할 수 있다.

필수 검사는 티켓 생성과 계획 전체 편집에 적용한다. 기존 티켓에 새 필수 필드가 비어 있으면 다음 계획 편집에서 입력한다. 실행 전용 수정과 댓글은 차단하지 않는다. 비활성 필드와 숨겨진 필드의 값을 단순 편집으로 지우지 않는다.

## 화면 흐름

워크스페이스에서 티켓 필드 설정으로 진입한다. 관리자는 표준 필드와 커스텀 필드를 편집하고 저장 전에 입력 구성을 확인한다. 일반 멤버는 설정을 조회한다. 생성·계획 편집에 같은 설정을 적용하고 상세 화면에 저장된 추가 정보를 표시한다.

설정을 저장하면 해당 워크스페이스의 설정 쿼리를 갱신한다. 저장하지 않은 티켓 초안은 유지한다. 사용자에게 노출되는 이름과 시스템 식별자는 구분한다.

## 계약과 저장

- `GET/PUT /api/auth/workspaces/{workspaceId}/ticket-fields`: `{workspaceId, revision, standardFields, customFields}`.
- 표준 필드: `{key, label, description, visible, required, order}`.
- 커스텀 필드: `{key, type, label, description, active, required, order, options: [{value, label, active}]}`.
- 티켓 조회·저장에 `customFields`를 추가한다. 키별 값은 문자열·숫자·null이다. 기존 요청에서 이 항목을 생략하면 저장된 값을 보존한다.
- 새 폼은 `fieldRevision`을 보낸다. 설정 변경 시 409 `TICKET_FIELDS_CHANGED`를 반환하고 초안을 유지한다. 기존 클라이언트가 revision을 생략하면 현재 정책으로 검증한다.
- 티켓의 기존 `version`과 필드 설정 `revision`은 별도로 검사한다. 워크스페이스 간 필드·선택지 참조는 거부한다.
- 오류 응답은 `{error, code, fieldErrors}`로 기존 문구를 유지한다. 커스텀 오류 경로는 `customFields.<key>`다.
- 백엔드 `ticketfield` 기능은 공개 계약을 통해 이슈 기능에 정책·검증을 제공한다. 프런트엔드도 기능의 공개 진입점으로 연결한다.

## 작업 단위와 검증

1. 디자인·기능 명세와 TODO 갱신.
2. 설정 저장·조회·충돌·권한과 커스텀 값 저장·검증.
3. 공통 폼 구성·Valibot 입력/응답 검사와 티켓 폼 적용.
4. 워크스페이스 설정 화면·티켓 상세 표시·안내 자료.
5. API·브라우저·접근성·호환·실제 화면 검증과 CI 확인.

다른 워크스페이스 격리, OWNER/ADMIN과 프로젝트 관리자 차이, 빈 숫자와 0, 잘못된 날짜, 비활성 선택지 유지, 숨긴 값 유지, 누락된 기존 요청, 필수값·설정 충돌·티켓 충돌을 검증한다. 계산 필드·첨부·다중 선택·커스텀 값 필터/정렬·일괄 데이터 변환은 후속 범위다. 독립 마일스톤은 기존 기획을 유지하고 이 작업 이후 진행한다.
