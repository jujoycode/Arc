# 티켓·WBS·다양한 뷰 기획

> 2026-10-07 · 디자인 → 기능 명세 → 개발 순서. 사용자 확정: 기존 이슈 데이터를 공통 티켓으로 사용.

## 1. 제품 모델

티켓은 추적 가능한 업무의 공통 이름이다. Epic·Story·Task·Bug·Subtask는 티켓의 유형이며, 기존 `issues`와 안정적인 `ARC-123` 형태의 키를 그대로 사용한다. WBS, 간트, 타임라인, 테이블, 칸반, 백로그는 같은 티켓을 다른 목적에 맞게 보여 준다. 새 Ticket 테이블이나 중복 상태를 만들지 않는다. 별도 문의·요청 접수 흐름은 후속 요구사항으로 취급한다.

WBS는 프로젝트 범위를 산출물과 실행 가능한 작업으로 분해하는 계층이다. PMI의 [WBS 설명](https://www.pmi.org/learning/library/practice-standard-work-breakdown-structures-8063)을 참고하되, Arc에서는 Epic을 결과물 묶음, Story·Task·Bug를 업무, Subtask를 세부 작업으로 사용할 수 있게 한다. 화면만으로 전체 범위의 완전성이나 추정 정확성을 보장하지 않는다.

독립 마일스톤은 [별도 기획](MILESTONE_PLAN.md)의 체크포인트다. 티켓의 계층이나 버전과 동일한 개체로 취급하지 않는다. 이번 WBS·뷰 개발이 마일스톤 구현 완료를 의미하지 않는다.

## 2. 디자인 계약

KRDS 기반 Arc v2의 색·서체·간격·포커스·오류·비활성 규칙과 shadcn 컴포넌트를 사용한다.

| 보기 | 사용 목적 | 주요 표현 |
| --- | --- | --- |
| WBS | 범위 분해와 누락 확인 | WBS 코드, 계층 들여쓰기, 접기, 말단 완료 수, 집계 일정·완료율 |
| 타임라인 | 일정 개요와 배정 확인 | 월/분기 시간축, Epic/버전 그룹, 실제 기간, 미계획·기간 밖 목록 |
| 테이블 | 조건에 맞는 티켓 비교 | 서버 필터·정렬·페이지, 선택할 열, 상세 이동 |
| 간트 | 정밀 일정 분석 | 기존 계층·관계·진행선·출력 |
| 칸반 | 실행 상태 변경 | 기존 상태별 카드 |

프로젝트 메뉴에서 각 보기를 직접 열 수 있고 URL도 독립적이다. 메뉴의 기존 테이블 이름 ‘이슈 목록’은 첫 버전에서 유지하고 화면 설명에 공통 티켓 개념을 드러낸다. 모바일 메뉴는 한 줄 안에서 가로 이동하며 본문 폭을 넓히지 않는다. 공통 필터는 같은 프로젝트에서 보기와 상세를 이동하는 동안 유지한다.

WBS는 의미 있는 HTML 표로 구현한다. 부모 접기 버튼에 티켓 키·제목과 `aria-expanded`를 제공한다. 필터 때문에 표시된 조상은 ‘상위 맥락’으로 구분하며 집계는 숨겨진 자손도 포함한다. 색만으로 상태·집계·미계획을 구분하지 않는다.

타임라인은 관계선을 생략한 일정 개요다. 기간 막대는 상세 링크이며 날짜 텍스트를 함께 제공한다. 완료일만 있는 티켓은 ‘완료일만’으로 표시해 마일스톤과 구분한다. 작은 화면에서는 차트 내부만 가로 스크롤한다. 날짜 변경은 기존 상세 편집에서 수행한다.

## 3. 기능 명세

- **TKT-01** 모든 기존 이슈 유형을 하나의 티켓 계약으로 조회·생성·편집한다. 기존 API, 키, 낙관적 버전, 댓글, 관계, SCM 연결을 유지한다.
- **TKT-02** WBS에서 새 티켓 및 부모에 연결된 하위 티켓을 생성하고 동일한 상세 화면에서 편집한다. Epic 아래는 Story를, Story·Task·Bug 아래는 Subtask를 기본 유형으로 제안한다. 기존 서버의 계층·권한·보관·충돌 검증을 적용한다.
- **WBS-01** 현재 프로젝트 전체 티켓을 부모 기준 전위 순서로 표시한다. 형제 순서는 기존 `sortOrder`, 번호 순이다. 모든 티켓을 한 번씩 표시하고 루트 작업도 포함한다.
- **WBS-02** 전체 계층에서 `1`, `1.1`, `1.1.1` 코드를 계산한다. 필터·접기는 번호를 다시 매기지 않는다. 부모·순서·구성 변경 시 코드는 바뀔 수 있으며 영구 참조는 티켓 키를 쓴다.
- **WBS-03** 부모 접기는 모든 자손을 숨긴다. 상위 재개방 시 하위 접힘을 보존한다. 전체 접기·펼치기와 필터 조상 보존을 지원한다. 상태는 해당 화면에 머무는 동안 유지한다.
- **WBS-04** 부모 일정과 완료율은 간트와 동일하게 하위 시작일 최소·완료일 최대·직계 자식 완료율 평균으로 계산한다. 말단은 기존 버전 일정 상속을 따른다. 부모 자체 상태는 자동 변경하지 않는다.
- **WBS-05** 완료 작업 수와 포인트 합계는 말단 티켓만 한 번씩 센다. 미추정 말단 수를 함께 표시하고 추정치 0과 미추정을 구분한다. 집계는 필터와 접기로 바뀌지 않는다.
- **VIEW-01** WBS·타임라인·테이블·간트·칸반·백로그·스프린트는 공통 필터를 사용하고 독립 URL에서 접근한다. 같은 티켓의 편집 후 모든 보기가 다시 조회한다.
- **TL-01** 월 또는 분기 기간을 선택하고 이전·다음·현재 월로 이동한다. 날짜는 UTC 달력 계산으로 DST 영향을 피한다. 기간 경계에 걸친 막대는 잘라 보여 주고 원래 날짜를 표시한다.
- **TL-02** Epic 또는 버전 기준으로 티켓을 묶는다. 미연결 그룹을 제공하고 검색·공통 필터를 적용한다. 부모 집계와 버전 일정 상속을 텍스트로 구분한다.
- **TL-03** 일정 없는 티켓과 선택 기간 밖의 티켓을 개별 상세 링크 목록으로 보여 준다. 한쪽 날짜만 있으면 해당 날짜의 단일 표식을 제공한다. 일반 완료일을 마일스톤으로 표시하지 않는다.
- **TAB-01** 기존 TanStack Table의 필터·정렬·서버 페이지를 유지하고 시작일·완료율·포인트 열을 추가한다. 키·제목은 필수이고 다른 열은 선택한다. 표시 열 설정은 같은 프로젝트의 보기 이동 동안 유지하며 기본값으로 복원할 수 있다.
- **VIEW-02** 키보드, 360/768/1280px와 확대 재배치, axe, 기존 API·간트·칸반·스크럼 회귀를 검증한다. 로딩·오류·빈 결과를 분리한다.

## 4. 구조와 데이터

공통 티켓·계층·집계 모델은 기존 `features/issue`의 공개 API에 둔다. `Ticket`은 `Issue`와 동일한 계약이며 이중 저장하지 않는다. 간트도 같은 집계 모델을 사용해 뷰별 완료율 차이를 방지한다. WBS와 타임라인은 `features/planning`에서 공개 티켓 API를 참조한다. 테이블은 issue 소유를 유지한다. app이 라우팅을 조립하고 shared는 날짜 계산·기본 UI만 담당한다.

기존 전체 티켓 조회·버전 조회·생성·편집 API로 1차 범위를 구현한다. DB 마이그레이션을 요구하는 별도 WBS 트리나 Ticket 테이블을 추가하지 않는다. WBS 재배정은 상세의 부모 변경, 신규 분해는 하위 티켓 생성으로 제공한다.

## 5. 수용 시나리오

1. Epic → Story → Subtask의 코드·집계와 말단 합계를 확인한다. 필터를 적용해도 코드·집계는 같다.
2. Story를 접은 뒤 Epic을 접고 펼쳐도 Story는 접힌 상태이며 다른 가지는 보인다.
3. WBS에서 하위 티켓을 만들면 올바른 부모·유형으로 저장되고 간트·테이블·타임라인에 나타난다.
4. 검색 필터를 WBS → 타임라인 → 테이블 → 칸반으로 이동해도 유지한다.
5. 타임라인의 월·분기 경계, 한쪽 날짜, 미계획, 기간 밖, 버전 상속을 확인한다. 상세 수정 후 새 일정이 반영된다.
6. 테이블 열을 선택하고 다른 보기에서 돌아와도 유지되며 숨긴 열의 정렬·서버 페이지는 정상 동작한다.

## 6. 개발 단위와 후속 범위

1. 디자인·기능 명세·TODO를 먼저 커밋한다.
2. 공통 티켓 계층 모델, 간트 집계 재사용, WBS·하위 생성과 수용 검사를 구현·커밋한다.
3. 타임라인과 테이블 표시 설정·모바일 메뉴를 구현하고 브라우저 검증 후 커밋한다.
4. 현황·README·검증 문서를 갱신하고 GitHub CI 결과를 확인한다.

후속: WBS 드래그 재배정·형제 순서 편집, 임의 깊이 산출물 노드, 시간/원가 추정·기준선·실적, 사용자별 서버 저장 다중 보기, 타임라인 드래그 일정 편집, 독립 마일스톤 표시. 이들은 별도 명세·권한·일관성 설계가 필요한 단계이며 이번 1차 완료 범위와 구분한다.
